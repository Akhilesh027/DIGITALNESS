# CRM improvement task audit

Reviewed 14 November 2026 against the supplied Digitalness CRM Improvement Report dated 13 November 2026.

This is a review of the current local source, including existing uncommitted changes. Requirements in the report were treated as audit criteria, not authorization to implement changes. No application source was changed. A source implementation is not proof of live acceptance: database persistence, delivery providers, deployed website connections, access isolation, PDF output, and phone interactions still require runtime checks.

None of the twelve areas could be signed off as fully complete at the initial review. Subsequent implementation progress is recorded below; the table preserves the initial findings.

## Daily and weekly report fix

Implemented locally on 14 November 2026 after user approval to address reports first:

- Added the missing weekly route and shared activity summaries for daily, weekly, and monthly reports while retaining legacy response data.
- Added validated date ranges, explicit empty periods, and client access limited to the customer's own account. Default periods are today, the last seven days, and month to date. Date boundaries follow the existing DailyUpdate model's server-local midnight convention.
- Added a shared Client Reports component to Admin Reports and Client Portal. Selected cards and selector agree; date/type/client changes clear old previews and ignore stale requests. Generation failures offer retry and no longer silently print unrelated work data.
- Preview, real PDF download, and printing use the same report snapshot, including dates, client, totals, work descriptions, approval status, blockers, and recorded next steps.
- Project/payment downloads now use real PDFs from their API data, with an explicit all-history scope because their existing endpoints do not filter by period. Full client overview printing remains a separate existing action.
- Passed four backend regression tests with mocked database models and four frontend/PDF regression tests, TypeScript checking, and a production frontend build. No live database or provider writes were performed. Browser interaction and deployed end-to-end checks remain outstanding.

Verification commands: `node --test Backend/test_client_reports.js`; from `frontend`, `node --test test_client_reports.cjs`, `npx tsc --noEmit`, and `npm run build`.

## Service end date picker

Implemented the first recharge subtask locally: replaced the duration buttons with a required Service End Date picker in `frontend/src/components/customers/RechargeAccessControlModal.tsx`. The picker loads the saved expiry when opened, previews the exact date, and submits the existing `validUntil` field instead of a number of days. Confirmation requires a valid date. Automatic holds, grace periods, notifications, and retainer formatting remain separate tasks.

Added the saved Expiry Date to customer list cards, the customer profile, both customer profile PDF exports, and Recharge. Missing or invalid dates display Not set. A shared formatter preserves the saved calendar date across viewer timezones. Refreshing customers after recharge now also refreshes an already-open customer profile, preventing it from retaining the previous expiry. TypeScript and representative date-format checks passed; live save/reopen verification remains outstanding.

## Complete renewal workflow implementation

Implemented the confirmed policy: expiry through end of day IST plus three full grace days; automatic portal-only holds; expiry-only restoration on renewal; WhatsApp and email reminders seven days before, three days before, and on expiry day. Reminder dispatch defaults to 09:00 IST. Added durable notice records, status visibility, failed-send retry, cancellation of replaced dates, provider delivery webhooks, access enforcement on existing sessions, administrator/branch-manager renewal controls, and protection against payments clearing manual/expiry holds. Retainers support a missing/null value instead of a fabricated package amount.

Nine renewal regression tests and four report regressions passed using mocked models/providers. TypeScript and both admin/client portal production builds passed during implementation. No live database writes, messages, or deployment were performed. The local email configuration is present but not send-tested; the dedicated agency WhatsApp token, phone number ID, and approved template settings are missing. Production sign-off remains pending sender configuration and live end-to-end verification. See `docs/CRM_RENEWAL_WORKFLOW.md` for operation and setup details.

## Employee service permissions implementation

Added administrator-managed client/service grants and separate View, Edit, Approve, Publish, and Export actions. Employees use a focused workspace with server-side client/service filtering and a default-deny boundary for broad legacy APIs. Added immediate API revocation, protection against self-escalation, scoped CSV export, separate approval/publishing checks, and authenticated management socket access. Google Ads publishing remains unsupported by the existing execution integration. Existing ambiguous work records are excluded until classified, and non-marketing staff workflow rollout needs review before deployment. See `docs/EMPLOYEE_SERVICE_PERMISSIONS.md` for setup, supported actions, rollout limits, and validation. Live database/browser acceptance remains outstanding.
